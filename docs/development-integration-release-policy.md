# 燕子持续开发、验证、合并与按需发布规范

生效时间：2026-10-10。适用于本机、笔记本、远程服务器、AI Agent 和 GitHub 自动化。**本文件是新的日常开发默认规则；遇到旧文档中“构建后强制重启”或“自动公开发布”的条款，以本规则为准。**

## 核心原则

**小步开发 → 及时验证 → 验证通过即集成 → 按需发布。**

Git Commit（保存开发过程）、Merge（集成已验证代码）和 Release / Deployment（交付或安装）是不同操作。**允许在验证前将 WIP Commit 提交到隔离功能分支**；**禁止将未通过合并门禁的变更直接纳入 main**。合并后不得自动安装、重启、打 Tag、推送 Release 或分发 APK，除非存在本次明确的发布/部署意图或具体已授权的自动化策略。

## 常态开发（不等到发布才提交）

1. **开始任务**：核对仓库 URL、当前分支、远程最新 HEAD、其他 Agent 的任务和工作区脏状态。本机、笔记本与服务器每个并行任务使用独立分支 / worktree；不得覆盖其他任务未提交代码。远程更新时先 fetch，检查 ahead/behind 和冲突风险。
2. **小步迭代**：每完成一个独立可追踪的功能、修复或重构，立即运行相应的快速静态检查与受影响模块的测试；WIP 可以在自己的分支多次 Commit，失败则继续修复。禁止为了避免提交而将多个无关任务长时间堆积在 main 工作树。
3. **集成门禁**：PR 或等价差异审查确认范围、安全性与机密信息，必须完成必要构建、关联测试、跨模块回归及 Git 冲突检查。失败时保留分支并继续修复；通过则及时合并到 main，不等正式版本发布。
4. **合并后**：确认 main 的 GitHub HEAD、CI 结果、镜像同步与本地分支差异；CI 尚未结束只能记录 pending，不能声称全部验证通过。发现失败应修复或回滚；记录 Commit/PR、测试结果及尚未验收的项目。不要因单一工作站 git pull 失败而覆盖它的文件。
5. **多设备**：GitHub main 是共享源代码的集成基准，不代表已安装的正式版本。各设备可按需安全更新；先备份/提交脏工作区，禁止覆盖别人的 WIP。正式安装包、个人配置、凭证、小程序数据使用各自既定的同步/发布机制，不应仅凭代码合并覆盖。
6. **共享功能开关**：未稳定的功能使用独立分支或明确的特性开关，不能以测试未通过为代价“先合并再说”。冲突必须逐处判断，禁止无审查直接 ours/theirs 全选。
7. **安全基线**：提交前检查 diff、token、Cookie、账号数据、配置文件和构建产物；密钥绝不入库。严禁 force-push main、以 reset --hard/clean 清除未经备份的他人变更。

## 验证层次与触发边界

| 阶段 | 触发时机 | 最低验收 |
| --- | --- | --- |
| 开发时 | 每个小修改 / WIP | 语法、静态检查、受影响单元/组件测试；必要时独立开发环境交互测试 |
| 合并前 | 功能准备进入 main | 编译、关联场景回归、敏感信息扫描、差异/冲突审查，关键跨模块测试 |
| 合并后 | GitHub 收到 Commit/PR | CI 成功与远程 HEAD 核对；失败阻止视为已验证的发布源 |
| 发布前 | 收到明确发布请求/满足具体已授权触发条件 | 锁定一个已通过合并门禁的 commit/tag，完整发布测试、版本与资产校验、备份/回滚预案 |
| 发布后 | 真正安装/更新/上线 | 安装、启动、健康检查、关键功能 smoke、实际样本验收；失败执行回滚 |

**发布可直接使用既有的已验证 Commit，无需为了“发布”再创建一个无意义的源码 Commit。** 版本文件、安装包配方或更新说明真的需要修改时，才产生新的 Release Commit 并重新运行受影响的发布验证。

## 发布与部署必须显式隔离

- **Windows 正式宿主**：默认不终止或重启正式 Yanzi 进程、不替换正式安装目录、不上传安装包、不创建或公开 GitHub Release；用户明确要求体验开发版，可隔离启动并验收；用户要求正式安装/发布，才执行相应的正式环境门禁。
- **Android / 笔记 / 相册等应用**：正常提交 main 不应触发 R2/APK 公共发布；通过明确的 workflow_dispatch 或其他具体批准的发布任务交付，需核对版本、签名及资产。
- **小程序和浏览器扩展**：开发阶段优先独立环境及热重载；有必要在当前机器验证网页/小程序时，先确认目标状态，不能将开发热重载等同公开发布。不得未经确认中断用户正在使用的正式实例。
- **Cloudflare 特殊例外（现状）**：`.github/workflows/deploy-cloudflare.yml` 目前在 main 的 `cloudflare/**`、`wrangler.jsonc` 等路径变更时自动部署生产 Worker（并可能执行 D1 migration），这不是纯代码合并。**在保留该机制期间，涉及这些路径的 PR 必须额外通过线上部署授权和迁移检查，再允许合并。** 禁止把 Cloudflare main push 描述为“肯定不会发布”。修改自动部署机制须另作明确决策。
- **GitHub Actions**：普通开发 CI、镜像同步不等于正式版本发布。发布工作流不能仅因修改源码或 workflow 文件就自动生成公开 Release；应以明确授权的手动触发 / 固定 Tag 发布门禁区分。

## 推荐结束报告

开发轮次：`task/branch`、Commit/PR、修改范围、快速测试与 CI 状态、合并结果、GitHub main SHA、设备本地同步状态、`releasePerformed: false`（除非真的发布）。

发布轮次再报告：版本号、源 Commit/tag、GitHub Release/资产链接、SHA-256、安装/线上健康、回滚位置与真实验收结果。明确标记 pending/blocked，不能以构建成功冒充已部署或已验证。

详细的正式部署安全操作仍需遵守 [生产部署与回滚门禁](continuous-improvement/PRODUCTION_DEPLOYMENT_POLICY.md)，但其旧版默认自动公开发布条款被本文件的“按需发布”取代。
