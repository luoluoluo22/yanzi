# 燕子持续开发、验证、合并与按需发布规范

生效时间：2026-10-10。适用于本机、笔记本、远程服务器、AI Agent 和 GitHub 自动化。**本文件是新的日常开发默认规则；遇到旧文档中“构建后强制重启”或“自动公开发布”的条款，以本规则为准。**

## 核心原则

**小步开发 → 及时验证 → 验证通过即集成 → 按需发布。**

Git Commit（保存开发过程）、Merge（集成已验证代码）和 Release / Deployment（交付或安装）是不同操作。**允许在验证前将 WIP Commit 提交到隔离功能分支**；**禁止将未通过合并门禁的变更直接纳入 main**。合并后不得自动安装、重启、打 Tag、推送 Release 或分发 APK，除非存在本次明确的发布/部署意图或具体已授权的自动化策略。

## 多 AI 开发任务强制收尾门禁（2026-10-22）

当前已发现：多个 AI 在不同 worktree 开发，代码完成和正式构建之间缺少必经的 main 集成环节。v1.0.40 正式包内置浏览器助手 0.5.63，而另一工作区已有未合并的 0.5.69，属于典型的“开发成果滞留在分支”问题。

**无论使用 ChatGPT、Antigravity、Gemini、浣熊 MCP，还是燕子内部的子 Agent，每次可交付的开发任务必须遵循同一事务：**

1. 在独立工作树完成开发和目标场景验收；只提交本任务经过检查的文件，不得抢占其他 Agent 的工作区或使用 `git add .`。
2. 调用 `scripts/finish-agent-task.ps1 -VerificationScript <仓库内的可重复验收脚本> -Apply`。脚本要求干净的已提交分支、最新 `origin/main` 基线、无敏感文件、测试通过，然后推送该分支、创建或复用 PR。
3. 在 PR 同时通过 `portable-contracts` 与 `desktop-and-worker` 等检查且 GitHub 判断可以无冲突合并时，脚本执行 squash merge。完成后重新 fetch `main`，验证实际合并提交已存在；才允许标记 `integrationStatus: merged`。
4. **冲突/失败/超时 ≠ 完成。** 发生阻断时保留分支、PR 与工作区，报告具体阻断原因和任务责任人，修复后再次执行。不得强制 `push --force` 或用 `ours/theirs` 整体覆盖他人的代码。
5. 生产 Cloudflare 后端路径、`wrangler.jsonc` 与部署 workflow 的变更会触发真实部署；默认阻止自动合并，只有明确批准生产部署后才允许 `-AllowProductionDeploy`，并执行专门的迁移与生产验收。
6. 自动合并 **不等于自动打包或部署**。Windows、Android、浏览器扩展的正式安装/发布仍需要独立发布门禁；正式发布只能从包含目标改动的已验证集成提交或经批准的发布提交构建。

示例（在功能分支的独立 worktree 中）：

```powershell
# 先提交自己已经测试的代码。默认只显示计划：
.\scripts\finish-agent-task.ps1 -VerificationScript .\scripts\test-your-feature.ps1

# 确认差异与测试后，执行推送、PR、CI 及自动集成：
.\scripts\finish-agent-task.ps1 -VerificationScript .\scripts\test-your-feature.ps1 -Apply
```

注意：仓库 GitHub 设置当前不启用原生 `allow_auto_merge`；脚本在 CI 通过后执行受控合并，而不是提前设置无条件自动合并。分支缺少独立可重复的验收脚本时，不具备“已开发完成”的定义。

### 每位 AI 的结束报告

必须附上：`taskId`、`branch`、`sourceCommit`、`prUrl`、`checks`、`integrationStatus`（`merged|awaiting-ci|blocked`）、`mainMergeCommit`（确实已合并时）、`releasePerformed`。主管 Agent 对未合并的子 Agent 结果应重新分派集成任务，不能仅汇总子任务为完成。

## 单一活跃工作区规则（2026-10-25 起）

为避免不同工作树中的功能已实现却未进入正式主线，**燕子宿主仓库从现在起只允许一个活跃的可写 Git Worktree**。所有开发任务在该工作区串行执行，GitHub `main` 是唯一集成与发布基准；允许保留功能分支作为 Git 引用，但不得为普通任务自行创建第二个 Worktree。确需临时隔离工作区时，先取得用户对本次例外的明确授权。

- 开始开发前检查 `git worktree list`、当前分支、未提交改动及其他任务占用；同一工作区被占用时排队，不抢写，不跨分支覆盖。
- 离开功能分支前先完成必要验证、定点提交与集成。每次正式发布前核对已完成但未集成的分支、关键用户级小程序与现有配置兼容性，并检查燕环动作、截图复制粘贴等历史高风险功能；不能只靠构建通过推断功能未丢失。
- 历史 Worktree 进入**冻结清理队列**：逐个记录独有提交、未提交/未跟踪文件、远端和活动引用，先备份/归档并完成可恢复性验证，再移除确定无独有价值的工作树。不得用 `reset --hard`、`clean` 或递归删除来满足“单工作区”数量目标。
- 完成历史清理前如实际仍存在多个 Worktree，必须如实标记“单工作区策略已生效、存量未清零”，不得宣称物理目录只剩一个。

## 常态开发（不等到发布才提交）

1. **开始任务**：核对仓库 URL、当前分支、远程最新 HEAD、其他 Agent 的任务和工作区脏状态。本机、笔记本与服务器同一仓库的写入任务须串行排队，遵守上面的单一活跃 Worktree 规则；不得覆盖其他任务未提交代码。远程更新时先 fetch，检查 ahead/behind 和冲突风险。
2. **小步迭代**：每完成一个独立可追踪的功能、修复或重构，立即运行相应的快速静态检查与受影响模块的测试；WIP 可以在自己的分支多次 Commit，失败则继续修复。禁止为了避免提交而将多个无关任务长时间堆积在 main 工作树。
3. **集成门禁**：PR 或等价差异审查确认范围、安全性与机密信息，必须完成必要构建、关联测试、跨模块回归及 Git 冲突检查。失败时保留分支并继续修复；通过则及时合并到 main，不等正式版本发布。
4. **合并后**：确认 main 的 GitHub HEAD、CI 结果、镜像同步与本地分支差异；CI 尚未结束只能记录 pending，不能声称全部验证通过。发现失败应修复或回滚；记录 Commit/PR、测试结果及尚未验收的项目。不要因单一工作站 git pull 失败而覆盖它的文件。
5. **多设备**：GitHub main 是共享源代码的集成基准，不代表已安装的正式版本。各设备可按需安全更新；先备份/提交脏工作区，禁止覆盖别人的 WIP。正式安装包、个人配置、凭证、小程序数据使用各自既定的同步/发布机制，不应仅凭代码合并覆盖。
6. **共享功能开关**：未稳定的功能使用独立分支或明确的特性开关，不能以测试未通过为代价“先合并再说”。冲突必须逐处判断，禁止无审查直接 ours/theirs 全选。
7. **安全基线**：提交前检查 diff、token、Cookie、账号数据、配置文件和构建产物；密钥绝不入库。严禁 force-push main、以 reset --hard/clean 清除未经备份的他人变更。

## 验证层次与触发边界

| 阶段 | 触发时机 | 最低验收 |
| --- | --- | --- |
| 开发时 | 每个小修改 / WIP | 语法、静态检查、受影响单元/组件测试；必要时独立开发环境交互测试 |
| 合并前 | 功能准备进入 main | 编译、关联场景回归、敏感信息扫描、差异/冲突审查，关键跨模块测试 |
| 合并后 | GitHub 收到 Commit/PR | CI 成功与远程 HEAD 核对；失败阻止视为已验证的发布源 |
| 发布前 | 收到明确发布请求/满足具体已授权触发条件 | 锁定一个已通过合并门禁的 commit/tag，完整发布测试、版本与资产校验、备份/回滚预案 |
| 发布后 | 真正安装/更新/上线 | 安装、启动、健康检查、关键功能 smoke、实际样本验收；失败执行回滚 |

**发布可直接使用既有的已验证 Commit，无需为了“发布”再创建一个无意义的源码 Commit。** 版本文件、安装包配方或更新说明真的需要修改时，才产生新的 Release Commit 并重新运行受影响的发布验证。

## 发布与部署必须显式隔离

- **Windows 正式宿主**：默认不终止或重启正式 Yanzi 进程、不替换正式安装目录、不上传安装包、不创建或公开 GitHub Release；用户明确要求体验开发版，可隔离启动并验收；用户要求正式安装/发布，才执行相应的正式环境门禁。
- **Android / 笔记 / 相册等应用**：正常提交 main 不应触发 R2/APK 公共发布；通过明确的 workflow_dispatch 或其他具体批准的发布任务交付，需核对版本、签名及资产。
- **小程序和浏览器扩展**：开发阶段优先独立环境及热重载；有必要在当前机器验证网页/小程序时，先确认目标状态，不能将开发热重载等同公开发布。不得未经确认中断用户正在使用的正式实例。
- **Cloudflare 特殊例外（现状）**：`.github/workflows/deploy-cloudflare.yml` 目前在 main 的 `cloudflare/**`、`wrangler.jsonc` 等路径变更时自动部署生产 Worker（并可能执行 D1 migration），这不是纯代码合并。**在保留该机制期间，涉及这些路径的 PR 必须额外通过线上部署授权和迁移检查，再允许合并。** 禁止把 Cloudflare main push 描述为“肯定不会发布”。修改自动部署机制须另作明确决策。
- **GitHub Actions**：普通开发 CI、镜像同步不等于正式版本发布。发布工作流不能仅因修改源码或 workflow 文件就自动生成公开 Release；应以明确授权的手动触发 / 固定 Tag 发布门禁区分。

## 推荐结束报告

开发轮次：`task/branch`、Commit/PR、修改范围、快速测试与 CI 状态、合并结果、GitHub main SHA、设备本地同步状态、`releasePerformed: false`（除非真的发布）。

发布轮次再报告：版本号、源 Commit/tag、GitHub Release/资产链接、SHA-256、安装/线上健康、回滚位置与真实验收结果。明确标记 pending/blocked，不能以构建成功冒充已部署或已验证。

详细的正式部署安全操作仍需遵守 [生产部署与回滚门禁](continuous-improvement/PRODUCTION_DEPLOYMENT_POLICY.md)，但其旧版默认自动公开发布条款被本文件的“按需发布”取代。
## 全量改动审计与防遗漏合并（2026-10-24）

主管 AI 在任何合并操作前，应执行 git worktree list、git branch -vv、各工作区 git status --porcelain、git log main..branch、git diff main...branch，并查看远端 PR/CI 状态。建立逐项台账（worktree、branch、文件/提交、任务、验证结果、集成决策），不能只处理眼前分支。

对已完成且测试通过的所有改动逐项提交、审查和合并到最新 main；遇到冲突则人工分析后验证，不能覆盖另一分支。对未完成或测试失败的工作保留 worktree/分支和变更，不得混入主线；对无关、敏感或明确废弃变更说明不集成理由。最后重新盘点全部工作区，对每个剩余差异标记 awaiting-integration / blocked / WIP，核对 origin/main 与本地 main 一致，再报告已合并项和未合并项。未完成全量审计不能宣称“全部改动均已合并”。
