# 燕幕布局停留在待上传的排查与修复

用户截图中的条目为 yanm.layout（燕幕布局与组件定义）。只读检查本机状态发现：对象接口可用，但 objectsAuthoritative=false；待上传记录累计尝试 106 次，最后尝试为 2026-09-02，expectedRevision=577，观察到的远端版本为 600，最近错误为空。版本 600 的设备标识与本机一致，当前本机基线也是 600。

直接阻塞：上一轮新增的手动上传入口要求 objectsAuthoritative=true，因此兼容模式即使具备条件 PUT 能力，也在发请求前被拦截。另一个问题是完整刷新中的燕幕读取只保留待上传队列，没有主动重试这些积压任务。界面把所有无错误的积压状态写成“联网后将继续同步”，无法说明真正原因。

修改：

- 手动上传使用 ObjectSyncAvailable 判断能否安全条件写入；不再把是否启用唯一对象来源当作上传前提。单向下载保留来源完整性要求。
- 对旧待上传版本，仅在云端来自本机、版本与本机已采用基线一致、原操作不是 expectedRevision=0 的创建时更新请求版本，仍由服务器执行条件写入；其他设备的版本不能自动套用。
- 完整刷新会重试待上传燕幕对象；同设备版本重新对齐最多再执行一轮，遇到真实错误不无限重试。独立下载按钮不进入这条上传链。
- 待上传详情提供明确的上传入口，不再笼统暗示网络断开。

数据体积约 49 KB，小于当前 Worker 实现的 1 MiB 限制；没有证据表明体积是此次原因。没有修改本机真实同步记录，也没有替用户向真实账号上传或选择冲突。

验证：独立构建 artifacts/yanm-upload-fix，0 错误，14 项现有警告；.NET 全量验证通过，新增兼容模式上传、下载来源约束、577→600 旧任务修复和禁止其他设备/创建操作自动重设版本的测试；本地 Worker 的 AuthorityMode=false 协议测试通过，覆盖实际条件写入、409、历史恢复和凭据过滤。当前运行的软件未替换，需要使用新构建后才生效。
